# N100 reference measurements

Measurements use the Intel N100 (four cores, 16 GB RAM), local SQLite/application storage and read-only SMB media. Existing household services remained running. These are prototype and playback checks, not complete release acceptance or a final backend selection.

## Matched SQLite prototypes

Both candidates use SQLite 3.54.1, identical fresh 10k/100k fixtures, case-insensitive indexed prefix queries, one database connection and 100-row JSON responses. The HTTP load client runs off-host through one persistent SSH tunnel. Candidate order is randomized. Each case has five repetitions of 2,000 requests, after readiness and ten warm-up requests. Caches are not evicted. The query mix is browsing and a prefix near the end of the library.

A measured query-plan bottleneck was fixed in both prototypes: matching the index and ordering collation enables a covering range search rather than a full index scan. The pre-fix baseline and optimized matrix are separate datasets. Neither comparison establishes a language-only effect.

The mixed workload adds incremental scans, 1 MiB HTTP range reads and one real-time VAAPI HEVC 1080p → H.264 720p / 3 Mbps transcode from the NAS. Core and FFmpeg CPU/RSS are recorded separately.

## Application playback

Intel VAAPI hardware decode/scale/encode passed using FFmpeg 6.1.1. QSV initialization failed with the installed runtime. AMD and NVIDIA remain unverified. The existing household media services were not changed.

The application scanned a small real NAS fixture and played a 1920×1080 HEVC BT.709 SDR source at a 60-second offset. Each mode ran three times with a loopback FFmpeg client, timing session creation through the first decoded frame. All nine checks passed.

| Mode | First decoded frame range |
| --- | ---: |
| Direct | 0.23–0.41 s |
| Single VAAPI HLS | 4.86–4.91 s |
| Adaptive VAAPI HLS (three renditions) | 5.23–5.29 s |

[Playback results](n100-playback.json), [hardware smoke checks](n100-hardware-smoke.json), [environment](n100-environment.json).

These timings include the FFmpeg client’s buffering. They are not browser/LAN startup measurements. HLS startup needs further investigation before making a user-visible startup claim.

## Interpretation and outstanding acceptance

- The 400-trial optimized matrix meets the 150 ms browse/search p95 target at every tested concurrency, through 100 concurrent requests, for both candidates. This is a bounded workload result, not a sustainable capacity limit.
- In the native SQLite comparison, Rust had lower paired p95 latency, CPU cost and RSS at concurrency 200. Go exceeded 150 ms p95 in some idle trials; Rust stayed below it in all tested trials. Trial medians alone conceal this variation.
- The native Go driver removes the Go-translated SQLite implementation as a confound. Driver bindings, scheduling, JSON encoding and build options still differ; results compare stacks rather than isolate language cost.
- The load generator, SSH tunnel, short trial duration, warm caches, synthetic ASCII metadata and shared household services limit inference. Establish longer steady-state saturation and repeat on separate days before selecting a backend.
- Cold-cache browsing, full-library scan throughput, browser playback startup, seeking/stalls, direct/remux/transcode concurrency, upload limits, real Nginx deployment and a pinned isolated Jellyfin comparison remain pending.
- No Jellyfin speedup, maximum stream capacity, AMD/NVIDIA support validation or production Rust feature parity is claimed.

Reproduce with `scripts/remote_worker.py` staged in the private benchmark workspace, then `scripts/remote_bench.py --host USER@HOST --key KEY --workspace /ABSOLUTE/WORKSPACE --requests 2000 --repetitions 5 --concurrency 1 10 25 50 100 --modes idle mixed-vaapi --output RESULT.json`. Build the additional native Go variant with `CGO_ENABLED=1 go build -tags sqlite_cgo -o bin/bench-go-cgo ./bench/go`, and select it using `--candidates go-cgo rust`. The host and private media paths are deliberately absent from published reports.
